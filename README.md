# ORKestrator

C++23 / Qt-приложение для выполнения задачи оркестром из семи ИИ-ролей через локальный LM Studio.

## Роли и контексты

| Роль | Работа |
| --- | --- |
| Исследователь проекта | Перед PM изучает инструкции, нужный код и конфигурацию, передает факты с источниками |
| Диагност | При сбоях выясняет причину или предлагает проверяемую гипотезу, возвращает отчет исходной роли |
| PM | Уточняет задачу через опросник, готовит декомпозицию и этапы с критериями приемки |
| PM-критик | Аргументированно проверяет план и возвращает его PM при существенных дефектах |
| Разработчик | Реализует текущий этап: читает и изменяет реальные файлы, запускает сборку и тесты |
| Критик разработчика | Проверяет реализацию этапа по файлам и результатам команд, возвращает замечания |
| Цензор | Проверяет всю задачу целиком, одобряет итог либо возвращает работу PM или на конкретный этап |

PM, PM-критик, исследователь и цензор сохраняют истории задачи. Разработчик и его критик используют отдельные контексты для каждой пары «редакция плана + этап»: повторное ревью продолжается в том же контексте, возврат цензора восстанавливает контекст выбранного этапа, новая редакция плана создает новые контексты. Каждое обращение к диагносту получает отдельный контекст. Полные активные и прежние истории сохраняются в журнале; между ролями передаются задания, результаты и отзывы.

```text
Исследователь проекта → PM ⇄ PM-критик
       ↓ план принят
для каждого этапа: Разработчик ⇄ Критик разработчика
       ↓ все этапы приняты
При сбое: исходная роль → Диагност → исходная роль
Цензор → одобрено: задача завершена
       → дефект плана: PM, затем повторная реализация по новому плану
       → дефект реализации: указанный этап и последующие этапы проходят заново
```

Этапы исполняются последовательно в порядке зависимостей. Неизвестные зависимости, дублирующиеся ID и циклы отклоняются. Предыдущие редакции плана, принятые реализации и все отзывы сохраняются в журнале сессии.

## Запуск

1. Загрузите текстовую instruct-модель в LM Studio и включите API:
   `lms server start --port 51325 --bind 127.0.0.1`.
2. Откройте `dist/Release/ORKestrator.exe` или exe из каталога сборки.
3. Укажите сервер (по умолчанию `http://127.0.0.1:51325`), обновите список моделей и назначьте модели семи ролям. Для пустого поля исследователя используется модель PM, для диагноста — модель разработчика. Одну модель можно использовать для всех ролей — контексты останутся раздельными.
4. Выберите **рабочую папку проекта**. Она должна уже существовать. Здесь разработчик будет изменять файлы и выполнять проверки.
5. Введите задачу или загрузите UTF-8 TXT/Markdown и нажмите «Запустить оркестр».
6. Ответьте на опросник. Ответ требуется на каждый вопрос; можно выбрать вариант, написать свой ответ или «не знаю». Существенные уточнения доступны также разработчику.
7. Наблюдайте за планом, реализацией, всеми ревью, командами и журналом. Завершенной считается только задача, одобренная цензором.

Для сборок MSVC запускайте приложение из Developer PowerShell for Visual Studio, чтобы дочерние команды получили среду компилятора. Qt и остальные зависимости рабочего проекта должны быть доступны его системе сборки.

Ключ авторизации задается в поле сервера или через `LM_STUDIO_API_KEY`. Он не записывается в настройки и историю сессии.

## Инструменты реализации

Разработчик может запрашивать `list_files`, `read_file`, `write_file` и `run_command`. Критик разработчика, цензор и два специалиста могут читать проект и запускать команды в пределах директив своей роли; прямой инструмент записи им недоступен. Исследователь ограничен изучением проекта, без сборки и тестов. Диагност не исправляет файлы и не устанавливает зависимости.

- Пути файловых инструментов относительны рабочей папке. Выход через `..`, абсолютные пути, доступ к `.git` и ссылки наружу отклоняются.
- Перед перезаписью существующего файла его нужно прочитать; если файл с тех пор изменился, перезапись отклоняется. Запись выполняется через `QSaveFile`.
- Инструменты работают с UTF-8 текстом до 256 КиБ за файл. Для больших файлов можно использовать диагностическую команду для выборочного чтения.
- Команда задается программой, массивом отдельных аргументов и относительной рабочей директорией. Автоматической оболочки нет; для shell-синтаксиса оболочку нужно вызвать явно.
- Команды выполняются асинхронно. В историю попадают фактические stdout/stderr, код завершения, признак таймаута и усечения вывода. Сохраняется до 64 КиБ конца вывода одной команды.
- Рабочая папка ограничивает файловые инструменты и текущий каталог процесса. Команды выполняются с правами пользователя; это не изолированная среда ОС.
- «Остановить» отменяет запрос модели и управляемый процесс команды. Уже выполненные изменения файлов остаются в проекте; автоматического отката нет.

Ошибка команды разработчика, критика реализации или цензора подключает диагноста. Два последовательных сбоя других инструментов либо повторные блокирующие ревью этапа также могут запустить диагностику. Результат и исходная ошибка возвращаются той роли, которая должна продолжить работу. Ошибки самого диагноста не запускают новую диагностику. При исчерпании лимита запросов диагноста возвращается отчет `incomplete`; причина не считается установленной. Ошибка API требует обычного повтора запроса. Описание тестов в ответе модели не заменяет журнал реального запуска.

## Директивы для локальных моделей около 30B

Системные инструкции ролей разбиты на короткие разделы с примерами JSON. Цель — уменьшить лишние итерации и неоднозначность протокола; измеренного ускорения или гарантии качества это не дает.

- PM уточняет только существенные неизвестные, не выясняемые из проекта, и формирует небольшие этапы с наблюдаемой приемкой.
- Разработчик последовательно получает результат чтения, записи и проверки. Один ответ содержит одну запись или команду либо до четырех независимых чтений.
- Повтор одинаковой операции требует новых фактов или изменений. После двух безрезультатных попыток требуется диагностика причины.
- Критики связывают blocking с конкретным местом, фактом и нарушенным требованием, не открывают закрытые замечания без основания.
- Проверки используют актуальные результаты; полная сборка и все тесты не повторяются каждой ролью автоматически. Цензор проверяет интеграцию и итоговую приемку.
- Короткие ответы уменьшают повторение данных в историях. Большой лимит токенов сохраняется как запас для кода.
- Пользовательские запреты разработчику сохраняются и входят в критерии ревью. Директивы направляют модель, но не создают изоляцию команд на уровне ОС.

Основание: [контекст и ясные инструкции](https://www.anthropic.com/research/effective-context-engineering-for-ai-agents), [простые агентные процессы и проверяемая обратная связь](https://www.anthropic.com/research/building-effective-agents), [протокол инструментов Qwen](https://qwen.readthedocs.io/en/latest/framework/function_call.html), [JSON Schema в LM Studio](https://lmstudio.ai/docs/developer/openai-compat/structured-output). Совпадение JSON со схемой не доказывает корректность реализации.

В интерфейсе доступен профиль генерации. «Авто по модели» распознает Qwen3.6 и Qwen3.8 и выбирает параметры с учетом режима мышления и роли. Для выключенного мышления: temperature=0.7, top_p=0.8, top_k=20, presence_penalty=1.5. Для Qwen3.6 с мышлением: разработчик и цензор используют coding-профиль temperature=0.6, top_p=0.95, presence_penalty=0; прочие роли — temperature=1.0, presence_penalty=1.5. Для Qwen3.8 с мышлением: temperature=1.0, top_p=0.95, top_k=20, presence_penalty=0. Repeat penalty остается 1.0. Для остальных моделей параметры остаются на стороне LM Studio. Можно явно выбрать настройки сервера, Qwen thinking или Qwen instruct (temperature=0.7, top_p=0.8, presence_penalty=1.5). Сам профиль параметров выборки не переключает мышление; для этого есть отдельный список «Мышление». Источники: [Qwen3.8-27B](https://huggingface.co/Qwen/Qwen3.8-27B), [Qwen3.6-35B-A3B](https://huggingface.co/Qwen/Qwen3.6-35B-A3B). Фиксированная temperature=0.2 больше не отправляется.

«Мышление → Авто по роли» сначала запрашивает /api/v1/models у LM Studio и проверяет allowed_options мышления, включая псевдонимы загруженных экземпляров. Если модель поддерживает выключение мышления, отправляется reasoning_effort=none для исследователя, PM, обоих критиков и диагноста. Это работает для GLM и других поддерживающих моделей без зависимости от имени. Разработчик и цензор используют режим сервера. «Выключить» явно отправляет none для любой модели; «Параметры LM Studio» не переопределяет мышление. Для моделей без выключаемого мышления автоматический режим оставляет настройки серверу. Если нативный API недоступен, выполняется совместимый запрос; для известных семейств Qwen3.5/3.6/3.8 и GLM4.7 остается резервное распознавание. Получение метаданных ограничено пятью секундами и отменяется при остановке задачи.

Служебные ответы ограничены отдельно: по умолчанию 8 192 токена у всех ролей, кроме разработчика. Разработчик сохраняет общий большой лимит. Поле «Служебный ответ» = 0 отменяет дополнительный предел. Бюджет мышления по умолчанию 24 000 символов, а не токенов; 0 отключает ограничитель. Он останавливает и длинное неповторяющееся рассуждение. В автоматическом режиме для моделей с выключаемым мышлением после превышения бюджета выполняется одна попытка без мышления с прежней историей; при явных настройках сервера задача останавливается для ручного изменения параметров. Счетчики ответа и мышления отображаются в строке состояния. Эти настройки не уменьшают число разрешенных итераций оркестра.

Ответы запрашиваются потоком SSE. Клиент ищет явные циклы слов и коротких фраз в ответе и в reasoning_content/reasoning и прерывает такой запрос. Одна автоматическая повторная попытка выполняется с прежней историей; повторное зацикливание переводит задачу в ошибку с возможностью ручного повтора. Отклоненные ответы не добавляются в рабочую историю, события сохраняются в generation_failures. Проверка эвристическая: она не обнаруживает все виды смыслового зацикливания. Содержимое файлов в actions разработчика исключено из проверки повторов, чтобы не отклонять допустимые повторяющиеся данные. Сервер, возвращающий обычный JSON вместо SSE, также поддерживается, но проверка тогда выполняется после получения ответа.

Оркестратор отдельно отслеживает циклы инструментов в каждом контексте. Если два последовательных пакета операций не дали новых данных, модель получает loop_control с требованием прекратить повторение. Следующий запрос уже известных неизменных данных блокируется до выполнения инструментов; для повторяющихся ошибок без доступного хеша блокировка выполняется после получения такого же результата. Наличие новых данных позволяет продолжить работу. У read_file неиспользуемые поля program/arguments и эквивалентные относительные пути не меняют смысл операции.

Повторные успешные чтения сохраняются полностью в tools журнала, но в рабочую историю вместо неизменного текста передается source_message — индекс исходного сообщения этого контекста, начиная с нуля. Перед блокировкой чтения проверяется текущий хеш файла или снимок каталога. Реальная запись файла меняет workspace_revision и разрешает новые проверки; перезапись теми же байтами прогрессом не считается. Для команд сравниваются фактические результаты и учитываются записи через инструмент файлов. События находятся в tool_loop_events. После остановки возможен ручной повтор той же задачи; счетчик застоя текущего контекста сбрасывается, история сохраняется.

JSON Schema содержит отдельные варианты actions/questions/ready с совместимыми обязательными полями и размерами массивов. PM-критик может вернуть только вердикт, без инструментов. При включенном JSON schema первый запрос исследователя дополнительно ограничен status=actions и list_files/read_file: готовый отчет или запуск оболочки на этом шаге схема не разрешает. После первого принятого запроса действий доступен обычный протокол исследования. Операции используют только нужные поля: type/path для чтения, content для записи, program/arguments для команды. Адаптер приводит компактные и прежние полные операции к внутреннему виду, не расширяя права роли. Однозначный запрос действий с пустым отчетом не считается выполненной работой, даже если модель ошиблась в status. Интерактивная оболочка без команды отклоняется.

Ошибочные ответы хранятся в exchanges, но не подаются обратно модели как примеры assistant. В исходное задание добавляется protocol_repair с точной причиной; валидные ответы и история задачи сохраняются. Контекст также содержит host_os, чтобы модель не угадывала оболочку.

Общие директивы разработчика действуют без дословного повторения в плане. Отсутствие повторения само по себе не является blocking; запрет новых файлов не расширяется на любые новые функции или классы внутри разрешенных файлов.

Новые системные инструкции применяются к новой задаче после пересборки приложения. Истории уже запущенной задачи не переписываются.

## Лимиты и повтор запроса

По умолчанию: 30 минут на ответ модели, 30 минут на команду, **65 536 токенов ответа**, 10 000 запросов PM, 100 000 запросов каждой другой роли на задачу и до 10 000 проверок на соответствующем этапе. Дополнительно: до 1 000 запросов исследователя, до 1 000 запросов на одно обращение к диагносту и до 1 000 диагностик на этап в каждой редакции плана. Эти лимиты доступны в интерфейсе; общий лимит запросов роли тоже действует. Лимит ответа в интерфейсе можно увеличить до 1 048 576, с учетом возможностей модели и ее контекстного окна.

Счетчики итераций в интерфейсе допускают значения до 1 000 000; таймауты — до 604 800 секунд (семь суток). Старые стандартные значения итераций автоматически заменяются увеличенными; пользовательские значения сохраняются.

Старое стандартное значение 12 000 токенов при первом запуске новой версии меняется на 65 536. Старый стандартный таймаут 300 секунд меняется на 1800.

При обрезанном ответе, таймауте или ошибке API измените параметры и нажмите **«Повторить запрос»**. Повтор выполняется в той же сессии, для той же роли, с сохранением текущего контекста, остальных историй, плана и ответов пользователя. Рабочую папку для повтора нужно сохранить прежней. При исчерпании лимита итераций результат остается промежуточным. Увеличьте соответствующий лимит и нажмите «Продолжить после лимита»: приложение возобновит ожидающий запрос или переход к ревью в той же сессии, сохранив контексты и счетчики.

Истории внутри одного контекста не обрезаются автоматически. Переход между этапами выбирает соответствующий контекст, сохраняя остальные в журнале. Разработчик и критик получают сведения о проверках текущего этапа и редакции плана, цензор — всех этапов текущей редакции. Эти сведения обозначают область проверки, но сами по себе не гарантируют актуальность результата после изменения файлов. Если исчерпано контекстное окно самой модели, ошибка сохраняется вместе с текущим состоянием; следует учитывать размер контекста выбранной модели.

## Сохранение

Состояние автоматически записывается в `%LOCALAPPDATA%/ORKestrator/ORKestrator/sessions`:

- `<id>.json` — версия схемы 3: семь ролей в `agents` с текущими контекстами и суммарными счетчиками `total_calls`; все контексты в `contexts`, исследование в `project_research`, отчеты диагностики в `diagnostics`, события зацикливания генерации в `generation_failures` и инструментов в `tool_loop_events`, задача, ответы, этапы, реализации, отзывы, инструментальные результаты и конфигурация без API-ключа;
- `<id>.md` — отчет с планом, реализацией, отзывами и фактическими результатами команд.

Папка открывается через «Файл → Открыть папку сессий». Экспорт JSON и Markdown доступен из окна. Журнал приложения находится рядом в `logs`. Чтение сохраненного JSON для возобновления после закрытия приложения пока не реализовано; повтор запроса работает в открытой задаче.

## Сборка

Используются C++23, Qt 6.4+, CMake 3.24+, Ninja, MSVC и spdlog 1.14. Стиль кода и исходные настройки взяты из `Digitizer_SW`; зависимости проекта находятся в локальной `libs`. spdlog ожидается в `libs/spdlog/Release` или `Debug`.

```powershell
Set-Location E:\DIGITIZER\iv02\ORKestrator
powershell -ExecutionPolicy Bypass -File .\build.ps1 -QtRoot E:\Qt\6.4.3\msvc2019_64
```

Скрипт собирает проект, запускает тесты и создает комплект `dist/Release`. Для Debug: `-Configuration Debug`; дополнительные параметры: `-LibsRoot`, `-SkipTests`, `-NoDeploy`.

Ручная сборка из Developer PowerShell:

```powershell
$env:QTDIR = 'E:\Qt\6.4.3\msvc2019_64'
cmake --preset release
cmake --build --preset release
ctest --preset release
cmake --install out/build/release --prefix dist/Release
```

На Windows `windeployqt` автоматически запускается после сборки ORKestrator для Debug и Release, используя механизм общей блокировки из Digitizer_SW. Qt DLL и плагины копируются рядом с exe. `cmake --install` дополнительно создает комплект в `dist`; `-NoDeploy` пропускает только этот дополнительный шаг.

Выбранная иконка встроена в Qt-ресурсы и Windows exe. Исходники: `resources/icons/orkestrator.png` и `orkestrator.ico`. Для повторной упаковки ICO из PNG используется `tools/make_icon.ps1`.

## Проверки

Автоматические тесты используют локальный HTTP-эмулятор и временные рабочие папки:

- опросник, возврат PM на доработку, выполнение этапов и возвраты цензора;
- раздельные контексты этапов, восстановление при возврате цензора, новые контексты при новой редакции плана и очистка для новой задачи;
- передача исследования PM, автоматическая диагностика, отсутствие рекурсивной диагностики, лимиты и возврат исходной роли;
- повторные и чередующиеся чтения, компактная передача неизменных данных, блокировка повторяющихся ошибок, восстановление после предупреждения, реальные изменения файлов и каталогов;
- SSE с разрывом UTF-8 между пакетами, остановка незавершенного потока при повторах, ограниченный повтор без повреждения истории, сохранение повторяющегося содержимого файлов, профили генерации, режим мышления по ролям, бюджет мышления и отдельный предел служебного ответа;
- реальные файловые операции, защита от выхода за рабочую папку и перезаписи изменившихся файлов;
- выполнение дочерних процессов, их вывод, таймаут и отмена;
- повтор обрезанного ответа и продолжение после лимитов запросов и ревью без потери сессии и ответов;
- JSON-протокол, зависимости этапов, ошибки API, лимиты и сохранение промежуточного состояния;
- полный сценарий интерфейса до одобрения цензором.

Ручной прогон реальной модели создает и меняет файлы в явно указанной тестовой папке:

```powershell
$env:PATH = 'E:\Qt\6.4.3\msvc2019_64\bin;' + $env:PATH
.\out\build\release\tests\lmstudio_smoke.exe 'qwen/qwen3.8-27b' '.\artifacts\smoke-sessions' 'E:\temp\orkestrator-smoke'
```

API: [Chat Completions](https://lmstudio.ai/docs/developer/openai-compat/chat-completions), [Structured Output](https://lmstudio.ai/docs/developer/openai-compat/structured-output).

## Структура

- `src/main` — интерфейс, модели семи ролей, рабочая папка, опросник и экспорт;
- `src/network` — асинхронный HTTP-клиент LM Studio;
- `src/orchestration` — протоколы, контексты этапов, исследование, диагностика, переходы, инструменты файлов и процессов;
- `src/saving` — атомарное сохранение состояния;
- `tests` — HTTP-эмулятор, интеграционные и интерфейсные сценарии.
