# ORKestrator

C++/Qt-приложение для первого этапа оркестра ИИ-агентов: уточнение задачи и получение декомпозиции, проверенной независимым критиком.

Проект расположен в `E:\DIGITIZER\iv02\ORKestrator`. Структура, C++23, Qt 6.4.3, spdlog, форматирование и исходный `.gitignore` взяты за основу из соседнего `Digitizer_SW`. Подключаются необходимые для этого этапа Qt Core/Gui/Widgets/Network и spdlog 1.14. Для тестов используется Qt Test.

## Запуск

Готовое приложение после сборки: `dist/Release/ORKestrator.exe`. Запускайте его из этого каталога вместе с DLL и папкой `plugins`.

1. Запустите LM Studio и загрузите текстовую instruct-модель. В текущем окружении установлена `qwen/qwen3.8-27b`.
2. Включите локальный API: `lms server start --port 51325 --bind 127.0.0.1`.
3. Откройте приложение. Адрес по умолчанию — `http://127.0.0.1:51325`; допустимо окончание `/v1`.
4. Нажмите «Обновить модели» и выберите PM и критика. Обоим агентам можно назначить одну модель; истории сообщений независимы. При JIT список API может включать незагруженные модели.
5. Введите задачу либо загрузите UTF-8 TXT/Markdown. Нажмите «Начать декомпозицию».
6. Ответьте на вопросы во вкладке «Опросник». Можно выбрать вариант, дополнить его или написать свой ответ. Ответ требуется на каждый вопрос; допустимо «не знаю».
7. PM может задать следующую группу уточнений. Когда план готов, автоматически подключается критик.
8. После одобрения во вкладке «Декомпозиция» появится итог. Его можно сохранить в Markdown, а всю историю — экспортировать в JSON.

Вкладка «Критик» содержит аргументированные замечания всех проверок, «Журнал» — ход работы. Интерфейс остается доступным во время генерации. «Остановить» отменяет запрос и сохраняет черновик.

При включенной авторизации LM Studio укажите ключ в поле сервера либо задайте `LM_STUDIO_API_KEY`. Ключ не сохраняется в настройках или сессиях.

## Как работает оркестр

```text
Задача → PM → опросник → ответы пользователя → PM
                                               ↓ готовый план
                               критик с новым контекстом
                                ↙                      ↘
                          доработать                  одобрено
                              ↓                           ↓
                       PM / новые вопросы        итоговая декомпозиция
```

Используется `POST /v1/chat/completions` LM Studio. «Сессии» — независимые истории сообщений, которыми управляет приложение, а не чаты в интерфейсе LM Studio.

- PM сохраняет свою историю, ответы пользователя и замечания критика.
- Для **каждой проверки критика** создаются два исходных сообщения: его системная роль и JSON с задачей, всеми ответами и текущим планом. История PM и предыдущие отзывы ему не передаются.
- Критик возвращает `approved` или `revise`. Возврат требует существенного замечания с проблемой, обоснованием и требуемым исправлением. Одобрение с таким замечанием считается ошибкой протокола.
- Ответ ограничивается JSON Schema. Приложение дополнительно проверяет JSON и согласованность полей; при нарушении делает до двух повторных запросов на исправление формата.
- Для модели без Structured Output можно отключить «JSON schema». Схема остается в системном сообщении, проверка ответа сохраняется.
- Таймаут, обрезанный ответ, ошибка API, отмена или достижение лимита оставляют результат черновиком.
- По умолчанию: 24 хода PM, 6 проверок критика, 12 000 токенов ответа, 300 секунд на запрос. Для медленной модели или reasoning увеличьте таймаут.

Этап ограничен декомпозицией. Исполнители подзадач, доступ агентов к файлам/командам, параллельное выполнение и возобновление незавершенной сессии пока не реализованы. Качество проверки зависит от выбранной модели критика.

Документация LM Studio: [Chat Completions](https://lmstudio.ai/docs/developer/openai-compat/chat-completions), [Structured Output](https://lmstudio.ai/docs/developer/openai-compat/structured-output), [List Models](https://lmstudio.ai/docs/developer/openai-compat/models).

## Сохранение

Каждое изменение состояния автоматически сохраняет `<session-id>.json` и `<session-id>.md`.

Каталог Windows: `%LOCALAPPDATA%/ORKestrator/ORKestrator/sessions`. Открывается через «Файл → Открыть папку сессий». Журналы приложения находятся рядом в `logs`.

JSON содержит задачу, ответы, версии планов, отзывы критика, историю PM, запросы/ответы и статус `approved`. Markdown включает задачу, уточнения, текущий план и последний отзыв. Неодобренные результаты помечены как черновики. Файлы записываются через `QSaveFile`.

## Сборка на Windows

Нужны MSVC с C++23, CMake 3.24+, Ninja и Qt 6.4+. spdlog берется из `libs/spdlog/Release` или `Debug`. Локальные зависимости расположены в папке libs. При сборке ничего не скачивается из сети.

Из PowerShell:

```powershell
Set-Location E:\DIGITIZER\iv02\ORKestrator
powershell -ExecutionPolicy Bypass -File .\build.ps1 -QtRoot E:\Qt\6.4.3\msvc2019_64
```

На Windows сразу после сборки цели ORKestrator автоматически запускается windeployqt: Qt DLL и плагины копируются рядом с исполняемым файлом в каталоге сборки (обычно out/build/release/src или out/build/debug/src). Это работает и при сборке из Qt Creator/Visual Studio, и через cmake --build. Применяется механизм из Digitizer_SW: POST_BUILD и общая файловая блокировка windeployqt.lock; ошибка развертывания останавливает сборку. Утилита ищется прежде всего в bin выбранного комплекта Qt. При необходимости ее путь можно задать через WINDEPLOYQT_EXECUTABLE.

Дополнительный шаг cmake --install создает отдельный комплект в dist/Release или dist/Debug. Параметр build.ps1 -NoDeploy пропускает этот шаг; автоматическое копирование Qt рядом с exe после сборки сохраняется.

Скрипт подключает MSVC, собирает приложение, запускает тесты и создает готовый комплект в `dist/Release`. Для Debug: `-Configuration Debug`. Дополнительные параметры: `-LibsRoot <путь>`, `-SkipTests`, `-NoDeploy`. Qt можно задать через `QTDIR`.

Вручную, из Developer PowerShell for Visual Studio:

```powershell
$env:QTDIR = 'E:\Qt\6.4.3\msvc2019_64'
cmake --preset release
cmake --build --preset release
ctest --preset release
cmake --install out/build/release --prefix dist/Release
```

Qt Creator: откройте `CMakeLists.txt` и выберите комплект Qt/MSVC. `ORKESTRATOR_QT_ROOT` и `ORKESTRATOR_LIBS_ROOT` переопределяют расположение зависимостей. Debug и Release используют отдельные каталоги сборки.

## Проверки

Автоматические тесты не требуют модели и Интернета. Локальный HTTP-эмулятор LM Studio проверяет формат запросов и переходы оркестратора:

- несколько раундов опросника и возврат на доработку;
- новый контекст критика при каждой проверке;
- исправление некорректного JSON и противоречивого вердикта;
- отмену и новый запуск, таймаут, HTTP-ошибку, обрезанный ответ;
- лимиты ходов/проверок и сохранение черновика;
- список моделей, UTF-8 и сохранение сессий;
- полный сценарий Qt-интерфейса: задача → опросник → ответы → одобренный план.

Ручная проверка реальной модели (тестовая задача с автоматическими ответами):

```powershell
$env:PATH = 'E:\Qt\6.4.3\msvc2019_64\bin;' + $env:PATH
.\out\build\release\tests\lmstudio_smoke.exe 'qwen/qwen3.8-27b' '.\artifacts\lmstudio-smoke'
```

## Структура

- `src/main` — окно, опросник, настройки и экспорт;
- `src/network` — асинхронный HTTP-клиент LM Studio;
- `src/orchestration` — роли, схемы JSON и цикл PM/критика;
- `src/saving` — атомарное сохранение;
- `tests` — интеграционные тесты и проверка реального сервера.

`.gitignore` дополнен исключением для отслеживаемого `CMakePresets.json` и правилами для `out`, `dist`, сессий и артефактов тестов. `.clang-format` скопирован из `Digitizer_SW`.
